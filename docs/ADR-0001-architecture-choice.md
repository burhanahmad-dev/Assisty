# Assisty — Architecture Decision Record (ADR-0001)

> **Note:** Infrastructure choices in this ADR are superseded by ADR-0002 (Supabase backend; see `docs/ADR-0002-supabase-backend.md`); the architecture SHAPE is unchanged.

**Chosen architecture:** Assisty Custom Cloud-Native (NestJS + Cloud Run / Fly.io / Railway + pgvector + Supabase Queues/pgmq)

## Why (philosophy)

Own the runtime, rent the models. Assisty is a custom cloud-native control plane: a stateless NestJS/Node API on Cloud Run / Fly.io / Railway as the synchronous edge (a long-lived Node process, NOT a Supabase Edge Function), a dedicated NestJS worker fleet driven by Supabase Queues (pgmq) + pg_cron for all inbound-message and AI work, Supabase Postgres with pgvector as the single system of record, and LiteLLM Proxy as the swappable model gateway. n8n is explicitly NOT the brain (see aiOrchestration); it is allowed only as an outbound integration the tenant can wire up. We optimize for three things in priority order: (1) hard per-tenant isolation and token security, (2) predictable horizontal scale on managed primitives, (3) cost control via an internal usage ledger that gates spend before Stripe ever sees it. The design deliberately stays on managed/hosted pieces (Cloud Run / Fly.io / Railway for the custom Node compute, Supabase Postgres, Supabase Queues/pgmq + pg_cron, Supabase Vault, hosted LLMs via LiteLLM) so a solo/small team can run it — no self-hosted frontier models, no Kubernetes, no Temporal until a real long-running-handoff use case forces it. (Upstash Redis + BullMQ is the kept-on-file alternative if richer queue semantics are ever needed.) Postgres + pgvector (not Qdrant) is chosen for the MVP precisely to collapse the system to one stateful store under one RLS security model; Qdrant becomes a swap-in behind the same Retriever interface only when vector volume or latency demands it. The backend platform decision is recorded in ADR-0002 (`docs/ADR-0002-supabase-backend.md`).

**Estimated MVP time:** ~15 weeks

**Estimated monthly cost:** ~$900-$1,500/month infra at ~50 active tenants (excludes pass-through LLM + WhatsApp costs, which tenants effectively fund). Rough breakdown: Supabase Postgres HA (2 vCPU / 8GB + storage/backups, pgvector + Supabase Queues/pgmq + pg_cron built in) ~$250-350; Cloud Run / Fly.io / Railway edge + worker + LiteLLM (3 services, min-instances warm, modest CPU) ~$200-350; Supabase Vault (pgsodium) + secrets store ~$10-30; networking/LB/WAF ~$50-100; logging/trace/monitoring ~$50-150. Stripe fees are a % of revenue (not infra). LLM inference via LiteLLM (text-embedding-3-small at $0.02/1M + GPT/Gemini chat) is pass-through and scales with traffic -- at ~50 tenants of moderate volume budget $300-800 of model spend, recovered in plan pricing, NOT marked up. WhatsApp per-message Meta fees bill to each tenant's own payment method = $0 to Assisty.

## Best ideas grafted in from the runner-up designs

- From Firebase-Native: keep the AI/embeddings/vector retrieval behind a strict Retriever interface AND a repository/data-access layer so the store is swappable — useful as the documented escape hatch if pgvector hits its scale ceiling and Qdrant must slot in (the winner already gestures at this; make it a first-class abstraction).
- From Firebase-Native: lean hard on first-party Supabase Auth (JWT) + FCM integration for the operator app (the winner uses Supabase Auth as identity-only; RLS policies read the tenant from a custom JWT claim, `auth.jwt() ->> 'tenant_id'`) — adopt the minimal-glue client wiring to claw back some of the winner's 15-week dev-speed deficit.
- From Firebase-Native: structurally-impossible-to-leak RAG via path/partition isolation is a strong mental model — in the winner, treat the tenant_id payload filter + tenant-led index as a hard partition, and add an automated test that proves a query without app.tenant_id set returns zero rows (turn 'structural isolation' into an enforced invariant, not just RLS trust).
- From n8n-Hybrid: adopt n8n explicitly as the INGESTION/re-embedding plane and as customer-facing OUTBOUND integrations (Sheets/CRM/Slack) — but ONLY if a tenant demand for no-redeploy ingestion iteration materializes; default the winner's ingestion to Supabase Queues (pgmq) + pg_cron (with light async/ingest tasks optionally on Supabase Edge Functions, Deno, 150s-capped) and add n8n later to avoid the premature dual-ops tax.
- From n8n-Hybrid: the discipline of Core-API re-validating and re-stamping tenant_id on EVERY write that originates from any less-trusted plane (ingestion jobs, batch re-embed, future n8n) — apply this server-side re-stamp pattern to all async workers in the winner as defense-in-depth even though RLS already backstops it.
- **Load-bearing role/connection warning:** Supabase `service_role` bypasses RLS (the same flaw that disqualified Firebase) — the edge and AI worker MUST use a dedicated tenant-scoped non-superuser role with RLS enforced (`FORCE ROW LEVEL SECURITY`) and `SET LOCAL app.tenant_id` per transaction, NEVER `service_role` for tenant data. Use Supabase's pooler (Supavisor) in transaction mode. The async-writer re-stamp rule above still applies on top of this.
- From n8n-Hybrid: add Langfuse (LLM tracing) to the winner's observability stack alongside Cloud Trace/OTel — per-turn LLM cost/latency/prompt tracing is materially more useful than generic traces for debugging the brain and tuning the spend-cap logic.
- From C1 (Firebase-Native): adopt its fastest-MVP staging mindset — keep purchase flows entirely out of the Android binary and lean on managed FCM + Supabase Auth (JWT, identity only) to minimize glue code, which C2 already does; also borrow C1's explicit, pre-planned escape-hatch discipline (a repository/data-access layer so the store is swappable) and apply it to C2's eventual pgvector->Qdrant swap so the migration blast radius is bounded by design, not retrofitted.
- From C1: the structural-isolation framing of per-tenant KB partitioning as 'the partition IS the isolation boundary' is a useful defense-in-depth complement — in C2, lead every pgvector index/filter with tenant_id AND consider a per-tenant partition/namespace convention so isolation is both RLS-enforced and structurally evident.
- From C3 (n8n-Hybrid): graft its 'n8n as async/ingestion + outbound-integration plane only, never the live turn' boundary explicitly into C2's roadmap, WITH the hardening rule that the Core API re-validates and re-stamps tenant_id on every n8n-originated write — this lets C2 offer no-redeploy ingestion/re-embedding flows and customer-facing CRM/Sheets/Slack exports without ever trusting n8n for isolation.
- From C3: add Langfuse for per-turn LLM tracing across the worker path (C2 lists Cloud Trace/OTel but not a dedicated LLM-observability layer) — concrete value for debugging RAG quality, token spend, and cap-breach forensics.
- From C3: the 'n8n admin behind SSO + VPC, no public webhook exposure for tenant data' posture is a good general control to apply to any internal/ops tooling C2 stands up later (re-embed jobs, admin batch tools).
- From Candidate 1 (Firebase-Native): the autoscale-to-zero / min-instances=1-only-on-the-hot-path cost discipline. C2's biggest weakness is its always-on floor (3 warm Cloud Run / Fly.io / Railway services + HA Supabase Postgres; the queue is now in-DB via Supabase Queues/pgmq, so there is no separate HA Redis floor). Keep min-instances=1 strictly on the webhook edge and AI worker, but let ingestion/embedding/billing-meter workers and the LiteLLM proxy (if cold-start tolerant via a fallback path) scale to zero to compress the ~$900–1,500 floor at low tenant counts.
- From Candidate 1: the explicit, pre-planned data-store escape hatch behind a repository/data-access abstraction. C2 should formalize the same swap-discipline it already implies with its Retriever and Channel interfaces — a thin persistence layer so the (acknowledged) future pgvector->Qdrant migration, and any read-replica/sharding move on Supabase Postgres, is a contained blast radius rather than a re-platform.
- From Candidate 1: structural (path/namespace) tenant partitioning of vectors as a defense-in-depth layer ON TOP of the RLS/payload filter. Even on pgvector, treat tenant_id partitioning (or partitioned tables) as a second structural barrier so a single forgotten WHERE clause cannot leak across tenants — pairing 'structurally impossible' with 'policy-enforced' is stronger than either alone.
- From Candidate 3 (n8n Hybrid): adopt n8n as the ingestion/re-embedding/outbound-integration plane explicitly and expose n8n/Make/Zapier as customer-facing OUTBOUND integrations — matching how real competitors actually use it. C2 already permits n8n here; C3's framing (and the 'Core API re-stamps and validates tenant_id on every ingestion-originated write' rule) is the right hardening pattern to codify for any async writer touching tenant data.
- From Candidate 3: add Langfuse (or equivalent) LLM-specific tracing alongside Cloud Trace/OpenTelemetry. C2's observability covers queue depth and latency but C3's per-turn LLM tracing (prompt, retrieved chunks, token/cost attribution per tenant) is valuable for debugging RAG quality, attributing spend to the usage ledger, and detecting prompt-injection/jailbreak attempts.
- From Candidate 1: distributed-counter / write-sharding awareness for the hot usage ledger. Even on Postgres, a viral tenant's per-message ledger increments + audit appends are a write hotspot; pre-plan ledger increment batching or partitioned counters so cap-enforcement writes don't bottleneck the worker transaction.
