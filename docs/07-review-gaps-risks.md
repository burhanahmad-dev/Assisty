# Assisty — Architecture Review: Gaps, Risks & Open Decisions

> Auto-generated by the completeness-critic pass of the architecture workflow.

## Verdict

CONDITIONAL GO. This is an unusually disciplined, internally-coherent architecture for a solo/small team — the core spine (stateless edge -> Supabase Queues (pgmq) + pg_cron -> stateless worker -> single Supabase Postgres+pgvector under RLS -> LiteLLM) is sound, the isolation story is genuine defense-in-depth, and 'cap before the model call' via an internal ledger is the right call. The backend platform decision is recorded in ADR-0002 (docs/ADR-0002-supabase-backend.md). The verdict against n8n-as-brain is correct and well-argued. BUT the plan is critically over-exposed to EXTERNAL dependencies it does not control (Meta Tech Provider approval, Business Verification/App Review, the Google Play cloud-software exemption) whose timelines and approvals are asserted as facts yet gate the entire revenue and margin thesis. Several load-bearing operational details (embeddings lifecycle, LangGraph state in a stateless worker, human-handoff/live-agent UX, the real Android payment-compliance flow) are unspecified, and there are real cross-doc inconsistencies (notably min-instances=1 on the worker fleet vs. the scale-to-zero/cost narrative, and GPT-vs-Gemini vs. a three-provider model menu). The 15-week MVP is aggressive-to-unrealistic given the multi-week-to-month Meta gating sits on the critical path. Fix the contradictions, write down the deferred operational specs, and de-risk the Meta/Play dependencies with a committed fallback before locking the timeline.

## Contradictions to resolve

- MIN-INSTANCES=1 ON THE WORKER FLEET vs. the cost/scale-to-zero narrative. AI Brain §1 and the Channels doc declare the AI Worker 'min-instances=1', but the Tech Stack doc frames async work as scale-to-zero ('Cloud Run / Fly.io / Railway Jobs for ingest / re-embed (scale-to-zero)') and the thesis is 'a solo team can run it cheaply.' A permanently-warm worker fleet + warm edge + HA LiteLLM + a managed Supabase Queues (pgmq) + pg_cron layer is a meaningfully higher baseline than implied; warm-worker latency vs. scale-to-zero economics is never reconciled.
- MODEL MENU INCONSISTENCY: Product Vision, AI Brain and Auth docs repeatedly say a tenant picks 'GPT vs Gemini' (two providers), but the Tech Stack diagram routes LiteLLM to 'OpenAI/Gemini/Anthropic' (three). Either Anthropic is tenant-selectable (then the product copy and per-plan model story are wrong) or it isn't (then the diagram is wrong). A builder doesn't know which providers to provision keys/budgets for.
- LEAN-vs-MULTICALL FRAMING: The Overview attacks n8n for '2-4 LLM calls per query' and AI Brain says 'Default chat = one LLM call', yet Assisty's own commerce path is a LangGraph multi-call 'bounded loop (lookup -> check -> answer)' plus an unaccounted memory-summarization call. The 'we are lean / they are bloated' framing is partly contradicted by Assisty's own multi-call paths; the per-turn call budget and its cap accounting are not reconciled.
- ISOLATION-MODEL FRAMING: Security doc says 'the only thing physically siloed per tenant is the encryption key boundary' and the row pool is 'fully shared', while the Data Model doc says write-hot tables are 'PARTITION BY LIST (tenant_id)' — i.e. rows ARE physically siloed per tenant by partition. LIST-partitioning by tenant_id also implies per-tenant DDL on every signup (a new partition), which cuts against the 'one schema, one migration, solo-operable' simplicity claim and is not addressed in onboarding.
- WEBHOOK URL SHAPE: The Overview says the edge receives 'one shared inbound webhook for all tenants' (singular), while the Channels doc shows 'POST /webhooks/:channel (ONE shared URL per channel)' (one per channel). Tenant resolution and Meta callback configuration differ between 'one URL' and 'one URL per channel'; a builder needs the exact shape.

## Gaps to close

- EMBEDDINGS LIFECYCLE is undefined. RAG 'embeds via LiteLLM' but no embedding model, vector dimensionality, or HNSW params are pinned, and there is NO re-embedding/migration story. pgvector columns are fixed-dimension; if the embedding model changes (or embeddings are keyed to a provider and a tenant switches GPT<->Gemini) every chunk must be re-embedded. The 'embeddings-ingest' queue exists but embedding versioning/backfill is unspecified — a builder cannot define the vector column without this.
- HUMAN HANDOFF and the LIVE-AGENT experience are named as a tool ('human handoff') and a Supabase Realtime (Postgres CDC over WebSocket) dashboard (SSE kept only as a fallback), but the flow is undocumented: how an operator takes over a thread, how the AI is paused/muted for that conversation, assignment/presence, and how the 24h WhatsApp window is managed while a human is typing. For a customer-SERVICE product this is core, not a footnote.
- CONVERSATION MEMORY mechanics are hand-waved ('short-term + long-term summary Postgres'). No spec for when/how summaries are generated (another LLM call?), whether that call counts against the cap, summary size limits, eviction, or how memory is erased on GDPR delete. The summarization cost is absent from the cap accounting.
- THE ACTUAL ANDROID PAYMENT/CHECKOUT FLOW behind the margin thesis is asserted, not designed. 'All checkout on web, never in the Android binary' + Stripe-gated onboarding implies an app that redirects to external web checkout — a narrow, contested Google policy area. No redirect UX, no Play-review-risk handling, no end-to-end spec for how a tenant attaches their own payment method to WhatsApp.
- DISASTER RECOVERY / OPS gaps: PITR is mentioned but no RTO/RPO; no LiteLLM / Supabase Queues (pgmq) failure runbook; no DLQ drain / poison-message procedure; no per-tenant app-key (AES-256-GCM crypto-shred) / Supabase Vault rotation procedure; no plan for scaling the single Supabase Postgres instance past vertical limits or surviving a regional outage. 'One store' is an operational strength and an availability single-point-of-failure — the trade is unaddressed.
- LANGGRAPH STATE in a stateless worker is unspecified. The commerce path is a 'bounded loop' with tools, but where LangGraph checkpoints state across the loop, what bounds it (max steps/tokens/wall-clock), and how it stays inside the single RLS transaction + cap accounting are not defined. A multi-tool loop needs an explicit state + cost model.
- TESTING/QA beyond the 'zero-rows-without-tenant' invariant test is absent: no latency/load validation plan, no answer-quality/grounding eval harness (despite Langfuse listed), no isolation fuzzing, no acceptance bar for guardrail/PII redaction effectiveness.
- RATE LIMITING / ABUSE at per-tenant and per-end-customer granularity is mentioned but not specified — no limits, no behavior when a tenant's own customers flood inbound, and no protection of the shared single edge/webhook from one noisy tenant degrading all tenants on the pooled model.

## Open product decisions for you

- Which models are actually tenant-selectable, gated by which plans, and which model does embeddings? 'GPT vs Gemini' (and maybe Anthropic) must become a concrete plan->model matrix, including whether the embedding provider is decoupled from the chat provider to avoid re-embedding on a model switch.
- Trial / free-tier policy and its guardrails. §7.1 cites a Stripe 'trialing' subscription, but the founder must decide trial length, whether channels can connect during trial (the 'subscribe before connect' rule implies yes once trialing), and the trial hard cap — this directly shapes abuse exposure since trials hold long-lived Meta tokens.
- Pricing/cap unit and at-cap behavior. What is the billable unit (resolutions? messages? tokens?) and what happens at the hard cap — templated 'over capacity' reply, silent queue, or operator alert + upsell? The ledger enforces the cap; the customer-facing degradation behavior and upgrade path are unmade product decisions.
- MVP channel scope given Meta gating. Decide explicitly whether to launch WhatsApp+Web+Email only and ship IG/Messenger later (the Channels doc recommends this). This materially changes the value prop and should be a committed decision, not left implicit behind 'App Review takes weeks to months'.
- Agency / multi-tenant-per-operator persona. Auth §1.6 hints a user may map to several tenant_ids. Whether resellers managing multiple businesses are an MVP persona is undecided and significantly affects auth, billing, and dashboard design.
- Data residency / region. A single Supabase Postgres instance implies a single region; the docs invoke GDPR erasure and cite EEA/UK markets. EU customer data in a US region is a sales blocker and a compliance decision the 'one store, one region' design forecloses by default — the target market must be chosen.
- Knowledge freshness for commerce. Is the product catalog a one-time uploaded snapshot (RAG over a frozen doc) or a live-synced source (Shopify etc.)? This is core to the 'commerce/multi-tool' path and is unspecified.

## Top risks

- EXTERNAL APPROVAL ON THE CRITICAL PATH (top risk). The revenue funnel and the headline 'zero messaging markup' margin depend on (a) approved Meta Tech Provider status, (b) Meta Business Verification + App Review (the docs say 'weeks to months'), and (c) the Google Play cloud-software exemption holding. None are under Assisty's control, all gate launch, and the 15-week MVP assumes timely resolution. Mitigate with Day-0 submission and an explicit fallback (BSP path, or web-first launch).
- MARGIN THESIS IS POLICY-DEPENDENT AND FRAGILE. 'No Google service fee' rests on keeping all checkout on web and out of the Android binary — a narrow, actively-enforced, frequently-changing Google policy. If Google reclassifies or the redirect UX trips review, the 15-30% fee reappears and the differentiator evaporates. Model unit economics with the fee included as a downside case rather than treating the exemption as fact.
- POOLED-DB BLAST RADIUS + NOISY NEIGHBOR. One Supabase Postgres instance + one shared edge + one Supabase Queues (pgmq) layer is simple but is a single availability and performance domain for every tenant. A forgotten WHERE tenant_id, a runaway tenant's traffic, a hot partition, or an instance-level incident hits ALL tenants at once. The leak-vector defense is strong; the availability/noisy-neighbor side of 'one store' is under-mitigated (no per-tenant throttling spec, no read-replica/shard escape hatch, no regional-failover plan).
- TOKEN CUSTODY IS THE CROWN-JEWEL LIABILITY. Assisty stores effectively-non-expiring WhatsApp Business Integration System User tokens for every tenant. A DB-dump + key-access compromise would let an attacker hijack every tenant's WhatsApp/IG presence — reputational extinction. Supabase Vault (pgsodium AEAD, per-DB root key) plus an app-level per-tenant AES-256-GCM layer (whose key deletion is the crypto-shred / GDPR-erasure mechanism) is correct, but per-tenant app-key access-control, least-privilege role boundary, key rotation, and alerting on anomalous token decryption are unspecified and must be P0. LOAD-BEARING WARNING: Supabase service_role bypasses RLS (the same flaw that disqualified Firebase) — the edge and AI worker MUST use a dedicated tenant-scoped non-superuser role with RLS enforced and SET LOCAL app.tenant_id per transaction, NEVER service_role for tenant data. Use Supabase's pooler (Supavisor) in transaction mode.
- SCOPE vs. 15-WEEK TIMELINE. MVP as written = multi-channel adapters + RAG + memory + guardrails + PII + LangGraph commerce + Stripe metered billing with a custom ledger + Supabase Vault (pgsodium) + per-tenant AES-256-GCM crypto-shred + RLS/partitioning/invariant tests + Supabase Auth + onboarding funnel + a Flutter Android+Web dashboard — for a solo/small team in 15 weeks with Meta approval running in parallel. This is optimistic by a large factor; the real risk is a slipped date or silent corner-cutting on P0 security under deadline pressure.
- COST PASS-THROUGH AND CAP COMPLETENESS. The framing says LLM + WhatsApp costs are 'tenant-funded' via caps, but at-cap tenants get a degraded templated bot — a churn/reputation risk framed as a feature. With unmetered memory-summarization and multi-tool commerce calls, real per-resolution cost may exceed plan assumptions; verify the ledger captures EVERY call (embeddings, summary, each tool step) or caps will leak.
- GUARDRAIL / ANTI-HALLUCINATION EFFICACY IS UNPROVEN. Differentiation is 'transparency' and grounded answers, yet the guardrail layer (grounding/citation check, PII redaction, refusal fallback) is described as steps with no eval harness or accuracy targets. For a system answering on behalf of OTHER businesses' brands, a confident wrong answer is a liability that flows to the tenant; there is no documented measurement or acceptance bar.
